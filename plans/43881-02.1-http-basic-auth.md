# #43881 — Step 2.1: Extend PAT support to HTTP Basic auth

Part of [Personal Access Tokens](43881-personal-access-tokens.md). Requires
[Step 2](43881-02-authentication-and-authorization.md) to be done first (implemented, verified,
still uncommitted in the working tree as of this writing — check `git log`/`git status` for the
actual current state before assuming).

**Why this step exists:** Step 2's own plan contradicted itself — it had a verify item expecting a
PAT to authenticate "as HTTP Basic username," but also a hard constraint "do not touch the HTTP
Basic branch at all." The worker session correctly followed the explicit constraint and left HTTP
Basic alone rather than guessing, and flagged the resulting gap instead of silently picking a side.
Confirmed real, not hypothetical: HTTP Basic auth in `find_current_user` goes through a completely
separate code path (`authenticate_with_http_basic` → `User.find_by_api_key(username)` directly) that
never touches `api_key_from_request`, so Step 2's fix genuinely doesn't reach it. Today: a PAT
works via `?key=` param and the `X-Redmine-API-Key` header, but NOT as an HTTP Basic username, even
though the legacy API key still works that way — a real inconsistency, not a documented tradeoff,
since the whole point of PAT is to be a drop-in replacement for the legacy key GitHub/GitLab-style,
and the legacy key already supports this transport.

   ```ruby
   authenticate_with_http_basic do |username, password|
     user = User.try_to_login(username, password)
     # Don't allow using username/password when two-factor auth is active
     if user&.twofa_active?
       render_error :message => 'HTTP Basic authentication is not allowed. Use API key instead', :status => 401
       return
     end

     user ||= User.find_by_api_key(username)
   end
   ```

# #43881 — Step 2.2: Minitest coverage for PAT authentication, retire the Playwright API spec

Part of [Personal Access Tokens](43881-personal-access-tokens.md). Requires
[Step 2](43881-02-authentication-and-authorization.md) and
[Step 2.1](43881-02.1-http-basic-auth.md) to be done first (check `git log`/`git status` for the
actual current state before assuming either landed).

**Why this step exists:** `playwright/tests/personal-access-tokens-api.spec.ts` was only ever a
stand-in — it exercises the API auth wiring over real HTTP because no UI existed yet to test with
Playwright, not because that's the right permanent home for this coverage. Redmine already has a
real, idiomatic place for exactly this: `test/integration/api_test/authentication_test.rb`, a
Minitest integration test covering every existing auth transport (session, HTTP Basic
username/password, HTTP Basic API-key-as-username, API key as `?key=` param, API key as
`X-Redmine-API-Key` header, switch-user). PAT belongs there, in the same style, as first-class
coverage that runs with `rake test` like everything else — not as a separate out-of-band Node/
Playwright dependency. Once that real coverage exists and passes, the Playwright API spec is pure
duplication and should be deleted, not kept "just in case."

```
Repo: this Redmine checkout. Prerequisite: Step 2 (PAT wired into api_key_from_request) and Step 2.1 (PAT wired into HTTP Basic, via a shared find_user_by_pat_or_api_key-style private method) are both already done. Verify the HTTP Basic branch in app/controllers/application_controller.rb's find_current_user also resolves a PAT before starting; if it doesn't (i.e. only the ?key=/header path has PAT support), stop and report instead of proceeding as if Step 2.1 landed.

Goal: add real Minitest integration test coverage for Personal Access Token authentication, in the same file and style as the app's existing API auth tests, then retire the now-redundant Playwright API spec.

Part A — add tests

1. Read `test/integration/api_test/authentication_test.rb` in full first. This is the exact file and style to extend — a `Redmine::ApiTest::Base` integration test, using `User.generate!`, `Token.create!`, the `credentials(user, password=nil)` helper (from `test/test_helper.rb:428`, defaults password to the username itself), `get '/users/current.xml', :headers => ...`, and `assert_response :ok`/`:unauthorized`. Follow this exact style — do not introduce RSpec-isms, factory_bot, or any other testing pattern this file doesn't already use.

2. Add tests to this file (naming convention: `test_api_should_..._using_personal_access_token_...`, mirroring the existing `..._using_api_key_...` names right above where you add them):
   - Accept auth using a valid PAT as the `?key=` parameter (mirror `test_api_should_accept_auth_using_api_key_as_parameter`, but build the credential via `PersonalAccessToken.create!(user: user, name: '...', expires_on: 30.days.from_now).value` instead of `Token.create!(user: user, action: 'api').value`).
   - Deny auth using an expired PAT as the `?key=` parameter (create with `expires_on: 1.day.ago` — check the model actually allows creating with a past `expires_on`; if `validates_presence_of` is the only validation and there's no "expires_on must be in the future" validation, this works directly; if there IS such a validation you haven't seen before, use `update_column(:expires_on, 1.day.ago)` after creation instead, same trick Step 2's own verification used).
   - Deny auth using a revoked PAT as the `?key=` parameter (create, capture `.value`, then `.destroy`, then try to authenticate with the captured value).
   - Accept auth using a valid PAT as the `X-Redmine-API-Key` header (mirror `test_api_should_accept_auth_using_api_key_as_request_header`).
   - Accept HTTP Basic auth using a valid PAT as the username (mirror `test_api_should_accept_http_basic_auth_using_api_key`, i.e. `credentials(pat.value, 'X')`) — this one specifically proves Step 2.1 actually works, not just Step 2.
   - Deny HTTP Basic auth using an expired or revoked PAT as the username (pick one, mirror the deny-style tests above).
   - A scope-respecting test: find (do not invent) an existing role/project fixture in `test/fixtures/roles.yml` and `test/fixtures/projects.yml` with a small, known permission set suitable for this — check what fixture roles exist and what permissions they actually have before picking one, the same way you'd check any other fixture before writing a test against it. Create a PAT scoped to a permission that role's member *does* have, and one scoped to a permission that role does NOT have (or that isn't in the role's permission set at all), hit two different real API endpoints gated by those two permissions respectively (e.g. something read-only vs. something requiring an edit permission, following how other existing tests in `test/integration/api_test/` pick endpoints for permission checks — check a couple of those files for the pattern rather than guessing an endpoint), and assert 200 for the in-scope one and 403 for the out-of-scope one. This is the same scenario `playwright/tests/personal-access-tokens-api.spec.ts` already proves via a project it creates from scratch — here, prefer reusing existing fixtures over creating new projects/roles, matching this test file's own convention (it never creates a Project or Role, only `User.generate!` and tokens).
   - Confirm a legacy API key (`Token.create!(user: user, action: 'api')`) still authenticates unchanged after Steps 2/2.1's refactor — mirror the existing `test_api_should_accept_auth_using_api_key_as_parameter` test but note in a comment that this is a regression check post-PAT.

3. Run the whole file: `docker compose exec -T redmine bundle exec ruby -Itest test/integration/api_test/authentication_test.rb` (see environment note: no native Ruby on this machine, route everything through `docker compose exec -T redmine ...`; if the container isn't up, `docker compose up -d` from the repo root, and if it fails with a stale `tmp/pids/server.pid` "already running" error, delete that file first). Every test in the file — old and new — must pass. Paste the real output.

4. Run `bundle exec rubocop test/integration/api_test/authentication_test.rb` (via docker compose exec) and fix any offenses in the lines you added (leave any pre-existing offenses in untouched lines alone).

Part B — retire the Playwright API spec, only after Part A's new tests are actually passing

5. Delete `playwright/tests/personal-access-tokens-api.spec.ts`. Before deleting, diff what it covers against what you just added to `authentication_test.rb` and confirm every scenario the Playwright spec tested (valid/expired/scoped/revoked PAT, legacy key unaffected) now has an equivalent Minitest test — if you find a scenario the Playwright spec covered that you haven't ported, add it to `authentication_test.rb` first rather than deleting coverage.

6. Run the remaining Playwright suite to confirm nothing else references or depends on the deleted spec: `cd playwright && npx playwright test`. Should show only `smoke.spec.ts`'s tests now, all passing.

Verify (final):
- Paste the full `authentication_test.rb` run output (Part A step 3, re-run once more after any rubocop fixes).
- Paste the Playwright run output from Part B step 6.
- Confirm via `git status` that `playwright/tests/personal-access-tokens-api.spec.ts` shows as deleted and `test/integration/api_test/authentication_test.rb` shows as modified — nothing else.

Constraints:
- Do not touch application_controller.rb, or any file other than `test/integration/api_test/authentication_test.rb` (Part A) and deleting `playwright/tests/personal-access-tokens-api.spec.ts` (Part B).
- Do not add a new test file — extend the existing `authentication_test.rb`, matching Redmine's own convention that this file is the home for API-transport-level auth tests.
- Do not commit. Leave changes in the working tree for review.
- If something about the existing fixtures makes the scope-respecting test awkward to write without inventing new fixture data, stop and report the specific difficulty rather than adding a new Project/Role fixture on your own initiative — that's a bigger decision than this step should make unilaterally.
```
